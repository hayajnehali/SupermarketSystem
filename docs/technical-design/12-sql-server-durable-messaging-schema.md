# TD-12 — SQL Server Physical Schema for Durable Messaging

**Version:** 0.1  
**Status:** Proposed for owner review  
**Scope:** SQL Server physical mapping for the durable messaging structures defined in TD-10 and the worker lifecycle in TD-11.  
**Database target:** SQL Server 2025; EF Core mapping is addressed separately.  
**Rule:** This is a physical design specification, not an executable migration. It does not change approved business behavior.

## 1. Database placement

| Object | Central DB | Each Branch DB | Purpose |
|---|---:|---:|---|
| `sync.OutboxMessages` | Yes | Yes | Durable outbound envelopes |
| `sync.InboxMessages` | Yes | Yes | Durable inbound receipts and processing state |
| `sync.ProcessedOperations` | Yes | Yes | Idempotency ledger for effects |
| `sync.BranchCommands` | Yes | No | Authoritative Central command-delivery ledger for branch polling |
| `sync.SyncCheckpoints` | Yes | Yes | Per-direction/per-stream progress |

**Ownership rule:** `BranchCommands` is the single authoritative delivery ledger for Central-issued branch commands. Do not also dispatch the same command independently from Central's generic Outbox. If a future internal event is used to create a BranchCommand, its creation and source-event consumption must be atomic and the BranchCommand remains the only branch-delivery record.

Branch databases contain no cross-database foreign keys to Central. `BranchId` is derived from authenticated service identity and validated against the local branch configuration; it is not trusted from an arbitrary payload.

## 2. SQL conventions

- Schema: `sync`.
- Surrogate primary keys: `bigint IDENTITY(1,1)`, clustered.
- Public message/operation identifiers: `uniqueidentifier`, generated by the application and protected by unique indexes.
- Hashes: `binary(32)` containing SHA-256.
- UTC timestamps: `datetime2(3)`; all application values are UTC and lease comparisons use SQL Server UTC time.
- State values: `tinyint` with explicit stable numeric constants in application code; do not persist localized enum names.
- Contract/type names and error codes: bounded `nvarchar`; payload/result bodies: `nvarchar(max)`.
- Mutable coordination rows include `rowversion` for optimistic concurrency.
- No cascade delete on messaging records. Retention/purge is a separately controlled technical operation and must preserve the replay/audit horizon.

The clustered surrogate key avoids using random GUIDs as the clustered key. Unique GUID indexes enforce identity without making the payload/coordination rows physically ordered by random identifiers.

## 3. Table definitions

### 3.1 `sync.OutboxMessages` — Central and Branch

| Column | SQL Server type | Null | Notes |
|---|---|---:|---|
| OutboxMessageId | bigint IDENTITY(1,1) | No | Clustered PK |
| MessageId | uniqueidentifier | No | Unique immutable envelope ID |
| OperationId | uniqueidentifier | No | Stable effect identity |
| MessageType | nvarchar(160) | No | Allowlisted contract name |
| SchemaVersion | int | No | Must be greater than zero |
| SourceSystem | tinyint | No | Central or Branch |
| BranchId | uniqueidentifier | Yes | Required for branch-originated scope; null for central-originated messages not owned by a branch |
| AggregateType | nvarchar(100) | Yes | Required only when ordered aggregate semantics apply |
| AggregateId | nvarchar(160) | Yes | Stable aggregate key |
| AggregateSequence | bigint | Yes | Positive sequence when ordering applies |
| CorrelationId | uniqueidentifier | No | Workflow trace |
| CausationId | uniqueidentifier | Yes | Causal predecessor |
| Payload | nvarchar(max) | No | Immutable versioned envelope body |
| PayloadHash | binary(32) | No | SHA-256 of canonical payload bytes |
| OccurredAtUtc | datetime2(3) | No | Event occurrence time |
| CreatedAtUtc | datetime2(3) | No | Insert time |
| DeliveryStatus | tinyint | No | Pending, Leased, Acknowledged, Quarantined |
| AttemptCount | int | No | Default 0; technical attempts |
| AvailableAtUtc | datetime2(3) | No | Default current UTC |
| LeaseOwner | nvarchar(200) | Yes | Worker instance |
| LeaseUntilUtc | datetime2(3) | Yes | Lease expiry |
| LastAttemptAtUtc | datetime2(3) | Yes | Diagnostics |
| AcknowledgedAtUtc | datetime2(3) | Yes | Durable acknowledgement |
| LastErrorCode | nvarchar(100) | Yes | Safe code only |
| LastErrorAtUtc | datetime2(3) | Yes | Diagnostics |
| RowVersion | rowversion | No | Concurrency token |

**Constraints and indexes**
- PK clustered on `OutboxMessageId`.
- Unique nonclustered index on `MessageId`.
- Check constraints: `SchemaVersion > 0`, `AttemptCount >= 0`, valid `DeliveryStatus`, and positive `AggregateSequence` when present.
- Filtered dispatch index for non-terminal rows, beginning with `DeliveryStatus, AvailableAtUtc, OutboxMessageId`; include `LeaseUntilUtc, MessageId, MessageType, BranchId`.
- Index on `CorrelationId`.
- Filtered unique aggregate sequence index on `AggregateType, AggregateId, AggregateSequence` where all three are non-null.
- Do not add a blanket unique `OperationId` constraint: one operation can legitimately emit multiple message types. Add a producer-specific unique key only where a particular event purpose is guaranteed once.

### 3.2 `sync.InboxMessages` — Central and Branch

| Column | SQL Server type | Null | Notes |
|---|---|---:|---|
| InboxMessageId | bigint IDENTITY(1,1) | No | Clustered PK |
| SourceSystem | tinyint | No | Authenticated source |
| MessageId | uniqueidentifier | No | Sender's stable message ID |
| OperationId | uniqueidentifier | No | Underlying operation |
| MessageType | nvarchar(160) | No | Allowlisted type |
| SchemaVersion | int | No | Positive |
| BranchId | uniqueidentifier | Yes | Validated scope where applicable |
| CorrelationId | uniqueidentifier | No | Trace |
| CausationId | uniqueidentifier | Yes | Causal predecessor |
| PayloadHash | binary(32) | No | Detect identity/content conflict |
| Payload | nvarchar(max) | No | Persisted only if required for asynchronous processing/replay |
| ReceivedAtUtc | datetime2(3) | No | Receipt time |
| ProcessingStatus | tinyint | No | Received, Processing, Applied, Rejected, Quarantined |
| LeaseOwner | nvarchar(200) | Yes | Inbox processor |
| LeaseUntilUtc | datetime2(3) | Yes | Recovery lease |
| AttemptCount | int | No | Default 0 |
| NextAttemptAtUtc | datetime2(3) | Yes | Technical retry schedule |
| ProcessedAtUtc | datetime2(3) | Yes | Durable outcome time |
| OutcomeCode | nvarchar(100) | Yes | Stable result |
| OutcomePayload | nvarchar(max) | Yes | Minimal replayable acknowledgement |
| LastErrorCode | nvarchar(100) | Yes | Safe diagnostic code |
| LastErrorAtUtc | datetime2(3) | Yes | Diagnostics |
| RowVersion | rowversion | No | Concurrency token |

**Constraints and indexes**
- Unique nonclustered key on `SourceSystem, MessageId`; the same MessageId from a different authenticated source remains distinguishable.
- Check constraints for positive schema version, non-negative attempt count, and valid processing status.
- Filtered work index on `ProcessingStatus, NextAttemptAtUtc, ReceivedAtUtc, InboxMessageId` for non-terminal states.
- Index on `OperationId, SourceSystem`; index on `CorrelationId`.
- A repeated `SourceSystem + MessageId` with the same hash returns the stored receipt/outcome. A different hash is an integrity conflict and must be quarantined/audited.
- If processing is synchronous in the receiving transaction, persist the final Inbox outcome in that same transaction as the domain mutation. If processing is asynchronous, the durable Received receipt is acknowledged as receipt only; the lease fields above recover stale Processing work.

### 3.3 `sync.ProcessedOperations` — Central and Branch

| Column | SQL Server type | Null | Notes |
|---|---|---:|---|
| ProcessedOperationId | bigint IDENTITY(1,1) | No | Clustered PK |
| ProcessingScope | nvarchar(100) | No | Stable module/application scope |
| BranchId | uniqueidentifier | Yes | Null only for central-owned scope |
| OperationId | uniqueidentifier | No | Idempotency key |
| OperationType | nvarchar(160) | No | Effect type |
| RequestHash | binary(32) | No | Canonical request hash |
| ResultCode | nvarchar(100) | No | Durable result |
| ResultPayload | nvarchar(max) | Yes | Minimal replay result |
| FirstMessageId | uniqueidentifier | Yes | First triggering message |
| CorrelationId | uniqueidentifier | No | Trace |
| CompletedAtUtc | datetime2(3) | No | Durable completion |
| RowVersion | rowversion | No | Concurrency token |

**Constraints and indexes**
- PK clustered on `ProcessedOperationId`.
- Unique filtered index `ProcessingScope, BranchId, OperationId` where `BranchId IS NOT NULL`.
- Separate unique filtered index `ProcessingScope, OperationId` where `BranchId IS NULL`.
- Index on `CorrelationId`; optional index on `CompletedAtUtc` for controlled retention operations.
- Same key and same hash returns the stored result; same key with a different hash is rejected as an idempotency conflict.
- Insert the ledger result in the same transaction as the protected domain effect. A committed incomplete placeholder must not be mistaken for a completed operation; if a multi-step asynchronous operation is required, its explicit state and lease must be designed rather than overloading this completed-result ledger.

Filtered indexes deliberately handle SQL Server nullable-key semantics and avoid relying on a generic nullable composite uniqueness assumption.

| CommandStatus | tinyint | No | Pending, Leased, Acknowledged, Rejected, Quarantined |
| CreatedAtUtc | datetime2(3) | No | Enqueue time |
| AvailableAtUtc | datetime2(3) | No | Poll eligibility |
| LeaseOwner | nvarchar(200) | Yes | Worker instance |
| LeaseUntilUtc | datetime2(3) | Yes | Technical lease |
| DeliveryCount | int | No | Default 0 |
| LastDeliveredAtUtc | datetime2(3) | Yes | Diagnostics |
| OutcomeCode | nvarchar(100) | Yes | Durable branch outcome |

| AcknowledgedAtUtc | datetime2(3) | Yes | Durable result time |
| RowVersion | rowversion | No | Concurrency token |

**Constraints and indexes**
- PK clustered on `BranchCommandId`; unique nonclustered `CommandId`.
- Unique `BranchId, OperationId, CommandType` for command types whose creation is once per operation.
- Poll index beginning `BranchId, CommandStatus, AvailableAtUtc, BranchCommandId`; include lease and command identity columns needed by the polling query.
- Index on `ReservationId`.
- Claim queries must filter by authenticated BranchId and eligible status/time, then atomically lease selected rows. Never select a branch scope from untrusted request JSON.
- Branch acknowledgements update the same command row; they do not create a second command identity.

## 4. State constants

Persist numeric values through explicit application constants and document them centrally. Initial proposed mappings:

| Entity | Value | Meaning |
|---|---:|---|
| Outbox DeliveryStatus | 0 | Pending |
| Outbox DeliveryStatus | 1 | Leased |
| Outbox DeliveryStatus | 2 | Acknowledged |
| Outbox DeliveryStatus | 3 | Quarantined |
| Inbox ProcessingStatus | 0 | Received |
| Inbox ProcessingStatus | 1 | Processing |
| Inbox ProcessingStatus | 2 | Applied |
| Inbox ProcessingStatus | 3 | Rejected |
| Inbox ProcessingStatus | 4 | Quarantined |
| BranchCommand CommandStatus | 0 | Pending |
| BranchCommand CommandStatus | 1 | Leased |
| BranchCommand CommandStatus | 2 | Acknowledged |
| BranchCommand CommandStatus | 3 | Rejected |
| BranchCommand CommandStatus | 4 | Quarantined |

A transport-level acknowledgement and a domain outcome remain separate concepts. For example, a durably received command whose domain result is Rejected is still a successfully acknowledged delivery; persist that distinction in the API response and command outcome fields. The numeric mapping is a technical contract and must not be casually reordered after deployment.

## 5. Transaction and concurrency rules

1. Domain mutation + Outbox insert: one local database transaction.
2. Inbox receipt + synchronous domain mutation + ProcessedOperations result + final Inbox outcome: one local transaction.
3. For asynchronous Inbox processing, commit receipt first; claim it using an atomic SQL update/claim query; then commit the domain effect, ProcessedOperations result, and final Inbox outcome together.
4. Branch command claim: one atomic Central DB statement/transaction that selects and updates the eligible rows with lease owner and expiry.
5. Branch command result: update the same BranchCommands row using CommandId and authenticated BranchId, guarded by valid state/concurrency conditions.
6. Checkpoint update: compare-and-update using RowVersion and contiguous sequence validation.
7. A unique-key race is expected under concurrent duplicate delivery. Catch only the relevant unique-key violation, reload the existing row, compare hashes, and return the recorded outcome; do not swallow unrelated database errors.

SQL Server claim implementations should use a reviewed `UPDATE ... OUTPUT` pattern or an equivalent transaction-safe pattern with appropriate locking (for example, `UPDLOCK` and `READPAST` where validated). The exact query must be integration-tested under the selected isolation level; a read-then-update sequence is not acceptable.

## 6. EF Core mapping requirements

- Map each table to schema `sync`; do not rely on convention-generated table names.
- Configure all unique/filtered indexes explicitly in model configuration and migrations.
- Map `rowversion` using `IsRowVersion()`.
- Configure UTC timestamp handling consistently; reject unspecified/local DateTime values at application boundaries.
- Treat payload and hash as immutable after insertion; update only delivery/processing metadata.
- Do not load `nvarchar(max)` payloads in polling list queries when the worker first needs only identifiers and metadata. Fetch payload for claimed IDs in a controlled query or return it only in the claim output.
- Avoid EF Core client-side claim filtering; claiming must be performed by an atomic database operation.
- Do not create cross-database foreign keys. Add local FKs only when both entities are owned by the same database and lifecycle.

## 7. Operational indexes and validation

Before production sizing, capture actual query plans and test representative volumes for:
- Pending Outbox dispatch and expired lease reclaim.
- Inbox receipt deduplication and stale Processing recovery.
- ProcessedOperations lookup under duplicate traffic.
- BranchCommands polling by BranchId and eligibility.
- Checkpoint compare-and-update.

Validate with concurrent integration tests for duplicate MessageId, duplicate OperationId, same key/different hash, two workers claiming simultaneously, lease expiry, late acknowledgement, and branch-scope isolation. Review index write amplification and retention/purge behavior using realistic branch traffic.

## 8. Explicit exclusions

This document does not define or change:
- Business reservation/payment/order/cancellation/refund behavior.
- Approved offline duration, reconnection, or resumption authorization.
- Customer delivery attempts or customer-facing deadlines.
- Retention duration or legal/audit policy.
- Application migrations or production DDL.

TD-12 is the proposed SQL Server physical schema baseline. Final DDL and EF Core migrations follow only after review and approval of the schema.
